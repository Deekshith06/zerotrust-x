# Data-quality reconciliation — 2026-09-15

## Scope

This note records the code-level reconciliation performed against the immutable
`data-quality-v1` baseline. It does not replace or modify that baseline, the raw
source files, or checked-in generated artifacts.

## Confirmed correction

The endpoint workbook contains two adjacent columns named
`detected_timestamp`. The second positional column is the source's resolved
timestamp. The previous reader used `dict(zip(headers, values))`, so the second
column silently overwrote the first and chronology checks could not run.

The reader now applies an explicit endpoint mapping:

- first `detected_timestamp` → `detected_timestamp`
- second `detected_timestamp` → `resolved_timestamp`

Unexpected duplicate headers fail closed. An isolated run from the original
source directory now produces the frozen quality findings:

|---|---:|
| Normalized events | 62,430 |
| Quarantine findings | 36,220 |
| Affected source rows | 29,536 |
| `RESOLUTION_BEFORE_DETECTION` findings | 268 |
| Duplicate findings | 1,430 |
| Detections generated by current pipeline | 1,473 |
| Risk identities generated by current pipeline | 3,000 |

The cleaning status remains `CLEAN_WITH_DOCUMENTED_EXCEPTIONS`.

## Provenance and manifest corrections

- JSON reader provenance now uses the same logical first-data-row convention as
  CSV/XLSX (`source_row=2`).
- Raw payload serialization uses the same canonical JSON representation as the
  raw-record SHA-256 calculation.
- The manifest hashes only the four declared ingested source files, records the
  optional notes file separately as `context_inputs`, and explicitly hashes all
  generated artifacts including quarantine output.
- A manifest schema version is recorded as `2`.
- Unrelated files such as `.DS_Store`, scratch files, and stale outputs are not
  silently treated as authoritative inputs or outputs.

## Frozen-boundary policy

`data/baselines/data-quality-v1.json` remains unchanged. The source files and
checked-in generated artifacts remain unchanged. Any future change to detection
eligibility, risk semantics, source identity policy, normalization rules, or
artifact metrics requires a new pipeline, artifact, and baseline version.

The current pipeline's detection/risk consumer population remains an explicit
compatibility decision: generated detections and risk currently use the full
normalized event view, while `clean_events.parquet` remains the clean-only audit
view. Changing that population would alter downstream semantics and must not be
done without a new versioned contract and reconciliation of detection/risk
counts and evidence IDs.
